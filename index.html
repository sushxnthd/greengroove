The system

( Green Groove )

We started with supermarket queues. The deeper question became: why reconstruct a shopper's basket only when they reach the register?

If identity, shelf events and cart state stay synchronized throughout the trip, checkout becomes confirmation of an already-known transaction.

Six layers. One trustworthy transaction state.

Each layer resolves one source of uncertainty:

01 / 06 · System layer

Identity

Give each shopper a unique RFID wristband so item events have a known cart context.

Why state?

The queue was the symptom. Manual reconstruction at checkout was the deeper problem.

  • Observe the aisle

    RFID identity, load cells and shelf readers turn a physical pick or return into an explicit event.

  • Resolve ambiguity

    Association connects each shelf event to the right shopper before the live cart changes.

  • Reverse safely

    Returns reverse earlier state instead of silently overwriting history, so the system can recover cleanly.

Engineering
lessons from the build

Detection is not association.

Challenge 01

Association

A shelf can tell us that an item moved; the harder problem is deciding which shopper changed it before the live cart is allowed to update.

Open explanation diagram ↗

Physical actions must be reversible.

Challenge 02

Reversibility

Shoppers return products and change their minds, so add/remove operations need explicit inverse transitions rather than silent corrections.

Open explanation diagram ↗

Sensors need a second opinion.

Challenge 03

Cross-checks

Shelf state and live cart state are two observations of the same transaction; disagreement can reveal missed, duplicate or ambiguous events.

Open explanation diagram ↗

Identity has to precede automation.

Challenge 04

Identity

An event without a reliable shopper or cart context cannot safely modify transaction state, even when the physical detection itself is correct.

Open explanation diagram ↗

Uncertainty should stay visible.

Challenge 05

Uncertainty

When an association is ambiguous, surfacing uncertainty is safer than silently forcing the event into the wrong shopper's cart.

Open explanation diagram ↗

Checkout was downstream of the real problem.

Challenge 06

Settlement

Once transaction state is maintained throughout the trip, final billing becomes settlement of known state rather than reconstruction from scratch.

Before a store pilot

What still needs to be tested?

Is Green Groove ready to run a supermarket?

It is a student-built prototype. Store-scale reliability, concurrent shoppers, sensor drift, ambiguous events and operational recovery need documented testing before a commercial rollout.

How are returns and uncertain events handled?

The system model keeps accepted pickups and inverse returns in an event history. An uncertain association stays on hold until resolved, rather than silently changing a shopper’s bill.

Are the graphics real product photographs?

The site currently uses technical illustrations. They explain the design and event logic; they are not photographs of installed hardware, app screenshots or evidence of field performance.

What does the interactive walkthrough show?

A browser-only model using example products and prices. It demonstrates pickups, returns, a held event and invoice confirmation. It does not connect to sensors, identify a person or collect payment.

What is the next milestone?

Controlled tests with documented conditions, event-level logs, error analysis and recovery checks, followed by field evaluation. Results will be reported with their test conditions.
