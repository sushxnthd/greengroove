Research frame01

The interesting problem wasn’t checkout.
It was state.

The project became more rigorous when we stopped asking only how to make shopping feel faster and started asking what the system would need to know, infer, reverse and trust.

Research question

Can a store build a reliable cart from physical events as the trip happens?

Instead of rescanning everything at the end, Green Groove models each pick or return as a state update tied to a persistent shopper session.

Design hypothesis

A transaction can be represented as reversible, identity-linked events.

If the identity, event and association layers stay aligned, the digital cart can accumulate through the trip rather than be reconstructed at checkout.

Evidence discipline

Unknowns stay unknown until they are tested.

This site separates the system concept, the failure modes we identified, external recognition, and the empirical questions that still need measurement.

System premise

Checkout starts before checkout.

If a product leaves a shelf, that physical action already contains information. Green Groove asks whether it can become the beginning of a transaction rather than something ignored until a scanner sees the item later.

System architecture02

One shopper.
One session.
Many events.

The system does not wait for the final counter interaction. It accumulates a transaction through four hand-offs, each of which can introduce its own failure mode.

01

Identify

An RFID-enabled band establishes a persistent shopper session.

02

Sense

Shelf-side sensing detects a product being picked up or returned.

03

Associate

The event is linked to the shopper and updates the live cart state.

04

Settle

The accumulated state becomes the basis for billing and inventory updates.

Failure-mode analysis03

The happy path was easy.
The edge cases made it engineering.

These are not presented as solved problems. They are the constraints that a credible implementation has to survive.

Returns

Every forward action needs an inverse.

Putting an item back must reverse the exact cart state created by the original pick event.

pick→return
Sensor disagreement

Uncertainty should stay visible.

RFID evidence and shelf-state change may arrive at different times or support conflicting interpretations.

Simultaneous actions

Detection is not association.

Nearby shoppers can create overlapping events. The system must determine whose cart should change.

Persistent identity

One identity has to survive the whole trip.

Repeatedly re-identifying the shopper at every shelf would recreate the friction the system is trying to remove.

Method04

How the project moved from an object to a system.

The strongest work was not adding more features. It was changing the level of abstraction: from a wristband and shelf to a state model with explicit assumptions and failure cases.

01

Frame the friction

Start from the repeated identity and scanning steps in conventional supermarket checkout.

02

Model the state

Represent the trip as identity-linked pick and return events that modify a live cart.

03

Stress the assumptions

Ask where ambiguity enters: disagreement, overlap, persistence, reversibility and delayed signals.

04

Prototype the explanation

Use product and visual artifacts to make the system understandable enough to critique and iterate.

My contribution05

I worked across the project, not inside one box.

Green Groove moved between research, systems thinking, interaction design and prototype communication. The tabs below separate those contributions instead of compressing them into one generic role.

01 / RESEARCH

Turned a broad “smart retail” idea into a specific systems question.

Mapped supermarket friction points, narrowed the scope, and helped define the assumptions that the concept would have to satisfy.

02 / ARCHITECTURE

Helped define the identity → event → cart → settlement flow.

Worked through return semantics, ambiguous events and the need to keep physical and digital state aligned.

03 / INTERACTION

Designed the band, shelf and cart as one continuous experience.

Focused on what the shopper should need to do, what should happen invisibly, and where the system should surface uncertainty.

04 / PROTOTYPING

Built the artifacts used to explain, critique and iterate on the concept.

Translated the system into product and visual forms that made weak assumptions easier to spot and discuss.

What I would test next06

A stronger project should make its next falsifiable questions obvious.

These are the measurements that would turn the current system concept into an empirical evaluation.

Association accuracy

Which shopper caused which shelf event?

Measure assignment accuracy as distance, crowding and simultaneous actions vary.

Return fidelity

Can inverse actions reliably restore cart state?

Track false additions, false removals and unresolved pick→return sequences.

Latency

How quickly does physical state become trusted digital state?

Measure event-to-cart delay and how latency affects ambiguity resolution.

Human factors

When should the system ask for confirmation?

Study the trade-off between invisible automation and surfacing uncertainty to the shopper.

Reflection
The first version was about a smart object. The better version was about keeping several states synchronized.

Green Groove made me think less about isolated “smart” products and more about systems: what each component knows, when it knows it, what can go wrong, and how a physical action becomes trusted digital information.

That shift—from object design to state reasoning—is the part of the project I would keep developing.
