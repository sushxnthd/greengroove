WHY IT EXISTS

Why identify every item twice?

Green Groove began with a simple observation: a supermarket already sees the moment a product leaves a shelf, but conventional checkout largely ignores that event and identifies the product again later.

The first version was about convenience. The more useful version became a systems question: can the transaction be assembled gradually while the customer shops instead of reconstructed at the end?

The interesting problem was not making checkout look faster. It was deciding what the system should know, when it should know it, and what happens when the physical world becomes ambiguous.
SYSTEM MODEL

Architecture

The transaction is distributed across four hand-offs. Each layer contributes state while the shopping trip is happening.

01

Identify

An RFID-enabled band establishes one persistent shopper session.

02

Sense

Shelf-side hardware detects a product being picked up or returned.

03

Associate

The physical event is linked to the correct shopper and updates the live cart.

04

Settle

The accumulated state becomes the basis for billing and inventory updates.

pseudocode 
01session = identify(RFID_band)
02
03on shelf_event(item, action):
04    shopper = associate(session, event)
05    if action == "pick":
06        cart[shopper].add(item)
07    if action == "return":
08        cart[shopper].remove(item)
01if RFID != shelf_signal:
02    flag("uncertain event")
03
04if multiple_shoppers_nearby:
05    resolve_association()
06
07if item_returned:
08    reverse_original_state_change()

Conceptual logic only. It summarizes the system model; it is not presented as production implementation code.

CORE CONCEPTS

Three product touchpoints

The original concept split the experience into three connected pieces rather than treating checkout as one device.

⌁

Groove Band

A persistent shopper identity that remains stable across the trip.

▦

Smart Shelf

The point where product movement becomes observable system state.

▤

Live Cart

A transaction record that updates continuously instead of being assembled only at checkout.

ENGINEERING NOTES

Edge cases changed the project

The most useful design decisions came from asking what breaks the clean happy path.

Returns are first-class events

A removal-only system is not enough. Putting an item back must reverse the exact cart state created by the original pick event.

Sensor disagreement

RFID evidence and shelf-state change may not arrive together or may point to different interpretations. Uncertain events should be preserved as uncertain rather than silently converted into transactions.

Simultaneous actions

Nearby shoppers can create overlapping events. Association logic matters as much as detection because the system must decide not only that something moved, but whose cart should change.

Identity must persist

Re-inferring the shopper at every shelf would recreate the same identification problem the system was trying to remove from checkout.

!
Systems lesson

A polished user interaction is only credible when the failure cases underneath it are credible too.

REFLECTION

What I took from it

The useful part of Green Groove was not the branding exercise. It was learning that a polished interaction only works when the invisible state underneath it is trustworthy.

The project made me think about what each component knows, when it knows it, what can go wrong, and how a physical action becomes reliable digital information. That systems perspective is the part I would keep developing now.
