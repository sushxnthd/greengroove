# Green Groove — Product Design Skill

## External design playbooks consulted
- https://github.com/anthropics/skills/tree/main/skills/frontend-design — subject grounding, deliberate typography, non-template aesthetics, critique.
- https://github.com/pbakaus/impeccable — design hierarchy, typographic rhythm, visual restraint, design anti-pattern audits.
- https://github.com/afterxleep/agents/tree/main/skills/pixel-perfect-design — implementation visual hierarchy, screenshot comparison, optical correction.

This skill is local project guidance **informed by**, not a full installed copy of, the above third-party skills. Read originals where possible before major visual changes.

## Hard design constraints
1. Green Groove is a **physical-first** RFID + load-cell shopping-state system, not a generic green-tech SaaS or futuristic checkout fantasy.
2. The canonical logo assets already exist; do not redraw or generate alternative logos.
3. Product photos show **one object / one action**. Most must have **zero baked-in words**; place explanatory text in semantic site HTML outside the imagery.
4. NO nine near-identical infographic tiles. Do not use glows, holograms, invented carbon metrics, generated certifications, fictional founders or synthetic retail pilots.
5. Strict separation of **concept photography** (label clearly), **real prototype photograph** (requires source), **software screenshot** (requires true app source), **technical vector** (requires verified logic), **institutional evidence** (requires original documentary support).
6. For visuals displayed in rotating 200–260px cards: identify subject at 220px, no tiny text, no small detailed charts.
7. Preserve existing Osmo-derived geometry and live accessibility. In-page typography belongs to actual editable DOM.
8. Treat highly saturated green as the **signal**, not the background. Use authentic materials: ABS/silicone, metal, load cell, wiring, packaging, produce.
9. Work in **3-asset evaluation batches**, reviewing a contact sheet and 220px display size before producing the remaining assets.
10. Avoid copying reference creative works; use them as critique methods only.

## Workflow — mandatory
- Inspect source website and existing visuals, then extract dimensions and placement intent.
- Write one-sentence visual thesis per asset and one concrete focal object/action.
- Pick family: object study / actual-use documentary / physical components / real software UI / technical diagram / verified proof.
- Make 3 genuinely different assets. Use real photography if available; generated render *cannot be promoted as evidence*.
- At 220px view, ask: can a viewer describe the subject in under 2 seconds? If no, simplify.
- Check no 2 adjacent cards use near-identical lighting, subject scale, camera angle or visual density.
- Produce responsive WebP/AVIF, preserve originals, document crop origin, semantics and alt.
- Browser screenshot QA at 390px, 768px, 1440px, including reduced motion; if browser blocked, flag QA **unverified** and do not approve integration.
- Compare before/after rather than asserting improvement. Mark review request and do not publish if user has rejected prior versions.

## Reject if any are true
- Looks like an overdesigned presentation slide instead of reusable site imagery.
- Requires paragraph-sized text to communicate its subject.
- Shows a feature not known to be implemented or a result not observed.
- 3D/AI render presents fictitious hardware as the real built system.
- User-supplied logo differs in geometry or color.
- CSS is hiding the actual image under pseudo-elements or a stale external background image.
- “Looks done” without a screenshot at the actual target resolution.
